Pool fix alone pushed the 100%-success ceiling from ~150 to ~260, roughly
doubling capacity. But latency at n=200-260 (~9s p50, ~16s p95) was
already brushing up against this test's 20s match-timeout — the pool
wasn't the bottleneck anymore above ~260, the matchmaker's OWN serialized
per-user DB calls were: MatchmakerQueue.tryMatch() processes the full
queue under a single lock, one await at a time, so at ~35-40ms per real
Neon round-trip, a 300-user pass took ~10-12s of DB latency ALONE before
any pairing logic — a structural ceiling no pool size fixes.

100% connection and match success at every size tested, through n=500
(the original target). Latency now scales with roughly n/3-n/4 ms instead
of n×35ms — because the matchmaker makes exactly ONE DB round-trip per
matching pass regardless of queue size (down from N), per-user cost is
now the in-memory pairing scan (Map/Set lookups), not network latency.

Root cause chain (both fixes were needed, in this order):
  1. Default pool size (10) caused connection-pool contention above ~150-200
     concurrent connections — fixed by raising max to 50.
  2. Once that was fixed, the matchmaker's own O(n) SEQUENTIAL DB round-trips
     per matching pass became the ceiling around n=260-300 — fixed by
     replacing N per-user queries with 1 batched query per pass
     (dbService.getBlockGraphForUsers), using a single
     "WHERE blocker_id = ANY($1) OR blocked_id = ANY($1)" query instead of
     N "WHERE blocker_id = $1 OR blocked_id = $1" queries.

Caveats (unchanged from before):
- Measures the LOCAL machine running the backend process, not production
  hosting tier capacity (Render free tier: 0.1 CPU, 512MB RAM, 15-min
  spin-down — see conversation discussion; not yet tested against the
  real deployment).
- Each round queues exactly N load-test users with no other real traffic
  competing for the same queue.
- The test-client process itself hit a V8 out-of-memory crash at ~540
  cumulative socket.io-client instances within one Node process during
  testing (not a backend issue) — mitigated with --max-old-space-size=4096
  for this client script; a real production backend doesn't have this
  constraint since it's not holding 500 *client* socket.io instances in
  one process, just 500 server-side connections.
- Two Firebase Admin API quirks were hit and handled during testing: an
  occasional "uid already exists" on createUser (a slow/retried request
  that had actually already succeeded — now treated as success, not
  failure) and an occasional "quota exceeded" on deleteUser under heavy
  consecutive load (now retried with backoff, and a "user not found" on
  retry is correctly treated as already-cleaned-up, not a failure).
  Verified zero orphaned test accounts after every run in this session.

backend running):
